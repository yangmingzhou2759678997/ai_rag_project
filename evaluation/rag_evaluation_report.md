# RAG检索与回答质量评测报告

## 1. 评测目的

本报告用于复盘当前项目的RAG检索与回答质量，并记录一次以实际失败案例为依据的最小优化过程。

评测的重点不是证明系统在任意企业数据上都具有固定准确率，而是回答以下问题：

- 当前固定测试资料能否被正确解析、切分和检索；
- 正确资料是否能进入向量粗排、Reranker精排和最终上下文；
- 最终回答是否正确、完整，并引用正确来源；
- 多文件、同名章节和多轮追问是否会发生混淆；
- 知识库中没有答案时，系统能否正确拒答；
- 优化前后使用同一批资料和问题时，结果发生了什么变化。

报告中的HTTP状态、关键词、来源和耗时来自CSV自动采集；严格正确性、完整性和来源纯净度来自人工复核。两类结果不能互相替代。

## 2. 项目RAG链路

当前RAG回答链路如下：

问题重写 → 问题向量化 → PGVector向量粗排Top-10 → Reranker精排Top-3 → 相关性阈值筛选与兜底 → 工具资料进入大模型上下文 → 流式生成最终回答 → 展示实际采用的参考来源

系统先读取当前会话的最近历史消息，再调用大模型把最新问题重写为独立问题。多轮问题的`setup_question`和正式问题使用同一个会话，不同题目和不同重复运行使用新的`session_id`。

问题重写失败时会回退到用户原始问题，避免整个请求直接中断。

重写后的问题先生成Embedding，再使用PGVector余弦距离检索候选片段。当前配置的粗排数量为Top-10。

每个候选片段保留：

- 正文`content`；
- 来源文件`source`；
- 原始片段编号`chunk_index`。

当前日志会打印粗排排名、来源、`chunk_index`和正文前120个字符，便于判断正确证据是否进入Top-10。

粗排候选交给Reranker重新评分，当前取Top-3。Reranker返回的原始`index`用于映射回完整候选片段，日志同时记录精排排名、相关性分数、来源和`chunk_index`。

正常情况下，只有达到相关性阈值的片段进入最终上下文。如果全部结果低于阈值，系统至少保留Reranker第一名；如果Reranker超时或异常，则降级返回向量粗排Top-3。

Agent把工具返回的资料加入上下文，再由大模型整理最终回答。回答只能使用工具资料；资料为空时应回复“抱歉，我在公司知识库中未找到相关信息”。

工具资料带有`【来源文件：文件名】`标记，最终回答末尾展示实际采用的参考来源。当前自动来源评测从“参考来源”部分提取文件名。

### 2.5 已完成的文档能力

当前项目已经实现：

- UTF-8 TXT解析；
- Markdown按普通文本解析；
- 普通DOCX解析；
- DOCX顶层段落和表格按文档原始顺序解析；
- 带文字层PDF解析；
- DOCX阶段、天、章、节的章节感知切分；
- DOCX Chunk继承`stage_title`和`section_title`；
- 元数据保存`source`、`file_type`、`chunk_index`；
- DOCX额外保存阶段标题和章节标题。

当前没有实现OCR、图片理解、扫描PDF识别、复杂嵌套表格还原、Elasticsearch、BM25、RRF、混合检索或模型微调。

## 3. 固定评测集设计

### 3.1 固定知识库资料

评测知识库只使用5份固定文档：

| 文件 | 格式 | 主要测试点 |
| --- | --- | --- |
| `rag_eval_basic.txt` | TXT | 普通段落、长文本、精确编号、最后一段 |
| `rag_eval_technical.md` | Markdown | 标题、列表、代码块、命令、最后一行 |
| `rag_eval_normal.docx` | 普通DOCX | 章节继承、同名第5天、跨Chunk、最后章节 |
| `rag_eval_table.docx` | 表格DOCX | 段落与表格顺序、空单元格、多行命令、章节继承 |
| `rag_eval_pages.pdf` | 文本层PDF | 4页、跨页事实、第3页空白、最后一页 |

每份资料都包含独有事实、精确编号或配置、长文本、文档末尾事实，以及与其他文件相似但答案不同的字段。这样既能测试基本命中，也能测试多文件消歧。

这些资料是专门设计的虚构评测数据，不代表真实企业业务规则。

### 3.2 固定问题

问题集共40题：

| 分类 | 题目数 | 正式运行数 |
| --- | ---: | ---: |
| 五种文件唯一事实 | 10 | 10 |
| 精确数字、编号、代码和命令 | 6 | 6 |
| 完整章节与跨Chunk | 6 | 12 |
| 多文件和同名章节消歧 | 6 | 8 |
| 最后一段、最后章节和最后一页 | 3 | 3 |
| 多轮改写 | 3 | 5 |
| 知识库外拒答 | 6 | 8 |
| 合计 | 40 | 52 |

Q017、Q021、Q022、Q024、Q032和Q038各运行3次，其余题目运行1次，因此完整基线共有52条正式记录。

`repeat_count`用于检查云端模型和检索链路的重复稳定性。一次答对可能是偶然结果；只有同一道题的全部重复运行都通过，才计入“问题级稳定通过”。

## 4. 优化前基线

### 4.1 CSV自动指标

从`rag_baseline_before.csv`重新计算得到：52条记录全部返回HTTP 200，没有脚本错误；平均关键词覆盖率为94.2%，关键词完整覆盖47/52；预期来源命中43/44，自动拒答通过8/8。
耗时方面，平均为11.14秒，P50为8.32秒，P95为28.21秒，最大为49.47秒。

来源命中的分母是44，因为8条拒答记录没有预期来源。关键词覆盖率是每条记录覆盖比例的平均值，“关键词完整覆盖”则要求该条记录的所有必需关键词都出现。

### 4.2 人工严格复核

人工复核采用“答案正确、内容完整、没有混入错误对象、来源可接受”的严格标准：

- 52条正式记录中严格完整通过46条；
- 严格运行级通过率为88.5%；
- 40道问题中35道在所有重复运行中均通过；
- 问题级稳定通过率为87.5%。

人工结果低于部分自动指标，说明关键词和来源文件名只能用于辅助筛查，不能直接等同于答案正确。

## 5. 失败诊断

失败定位不是只看最终答案，而是结合粗排、精排、最终上下文和问题重写日志判断故障层级。

| 问题 | 现象 | 主要故障层级 |
| --- | --- | --- |
| Q018 | 正确发布资料已召回，但回答混入其他文件的相似发布流程 | 跨来源内容污染、最终生成 |
| Q019 | 正确Chunk已经召回，回答遗漏精确配置值和校验词 | 最终生成完整性 |
| Q024 | 定向诊断中出现一次Reranker超时，粗排Top-3回退存在丢失正确表格来源的风险 | Reranker超时及回退 |
| Q029 | 明确询问TXT末尾信息，但正确TXT Chunk没有进入粗排Top-10 | 粗排召回 |
| Q032 | 目标切换时机械继承上一轮“询问配置”的谓词，部分回答还重复上一阶段内容 | 问题重写、最终回答范围 |
| Q033 | “下一天”指代偶发重写到错误章节 | 问题重写 |

五类故障的区别是：

- 粗排召回：Q029的正确TXT末尾Chunk没有进入Top-10，Reranker没有机会选择；
- Reranker超时及回退：Q024的定向日志出现过超时，粗排Top-3降级可能丢失排位更后的正确证据；
- 问题重写：Q032和Q033说明历史消息只能补全指代，不能机械复制上一轮谓词；
- 最终生成完整性：Q019的正确证据已进入上下文，但回答仍遗漏配置和校验词；
- 跨来源污染：Q018的正确Markdown已经找到，但模型把其他文件中的相似流程拼接进来。

本轮没有调整Reranker超时、Top-K或回退数量，因为这不是52条基线中的普遍失败模式，且检索参数已经冻结。

## 6. 实施的最小优化

本轮没有大规模重构，也没有修改Embedding模型、Reranker模型、Top-K、阈值、Chunk参数或数据库结构。

### 6.1 问题重写Prompt

问题重写增加了以下通用约束：

- 最新问题的属性、动作和目标优先；
- 历史消息只补全实体、文件、阶段、日期、章节和代词；
- 不机械继承上一轮的配置、时间、地点、人员等询问属性；
- 当用户只说“那另一个呢”“下一阶段呢”等目标切换表达时，改写为中性的“该目标的相关规定是什么”或“该目标具体如何处理”；
- 用户已经明确给出的文件类型、阶段、天数和顺序限制必须保留；
- 完整问题保持原意，不扩展额外问题。

问题重写的`temperature`由0.1改为0，使确定性改写任务尽量减少波动。

### 6.2 最终回答Prompt

最终回答增加了以下范围和完整性规则：

- 只回答最新的重写问题，历史消息只用于理解指代；
- 用户指定文件、实体、项目、阶段、日期或章节时，只使用匹配范围的资料；
- 完整流程题必须整合与目标直接相关的配置、步骤、校验词和复核要求；
- 多来源规则冲突时，不把不同实体的流程拼成一套规则；
- 先通过明确出现实体名称的片段确认可用来源文件；
- 同一已确认来源中的其他片段可以补全同一流程；
- 参考来源只列实际采用且通过范围核对的文件。

这些规则是通用约束，没有写死某道测试题、某个答案或某个固定文件名。

### 6.3 单一文件类型Metadata过滤

查询明确且只包含一种文件类型时，向量粗排增加`metadata_info.file_type`过滤。

当前支持：

- `TXT`对应`txt`；
- `Markdown`或`MD`对应`md`；
- `DOCX`或`Word`对应`docx`；
- `PDF`对应`pdf`。

如果查询同时出现多种文件类型，例如“TXT和PDF分别”，则不执行单一类型过滤，继续全库检索。查询没有明确文件类型时也保持原有全库检索。

如果过滤后没有任何Chunk，系统自动回退到原来的全库向量检索，以兼容缺少`file_type`的旧数据。该优化只限制候选范围，不修改问题文本、Embedding或Reranker。

现有文档的metadata已经保存无点号的`txt`、`md`、`docx`和`pdf`，因此不需要重新上传文档或重新生成向量。

### 6.4 为什么没有增加BM25、RRF或混合检索

当前评测没有证明存在普遍的粗排漏召回：

- 精确编号、配置、代码和命令类问题已经稳定通过；
- 主要粗排失败Q029有明确的单一文件类型范围，可以先用已有metadata解决；
- Q018的正确资料已经召回，问题是来源隔离和最终生成，而不是检索不到；
- Q019的正确Chunk也已经召回，问题是回答不完整。

因此本轮没有为了增加技术名词而引入新的检索链路。更复杂的检索只有在真实日志持续证明正确证据无法进入粗排Top-K时才有必要。

## 7. 优化后回归结果

### 7.1 CSV自动指标

从`rag_baseline_after.csv`重新计算得到：52条记录全部返回HTTP 200，没有脚本错误；平均关键词覆盖率为99.0%，关键词完整覆盖50/52；预期来源命中44/44，自动拒答通过8/8。

耗时方面，平均为9.14秒，P50为8.42秒，P95为14.15秒，最大为21.12秒。

### 7.2 人工严格复核

人工复核结果为：

- 52条正式记录中严格完整通过51条；
- 严格运行级通过率为98.1%；
- 40道问题中39道在所有重复运行中均通过；
- 问题级稳定通过率为97.5%；
- 知识库外拒答8/8；
- 多文件和同名字段消歧8/8；
- 文档末尾信息3/3；
- 多轮问题5/5。

### 7.3 唯一残留问题

优化后只有Q018的一次回答没有严格通过：

- 正确的目标Markdown资料已经召回；
- 一个无关表格DOCX片段也进入最终上下文；
- 模型偶发混入该文件中的相似通道和验收编号；
- 回答包含正确内容，但来源不纯净，因此只能判为部分正确。

这说明Prompt隔离可以降低混用概率，但当多个相似业务片段已经同时进入上下文时，它不是确定性的程序过滤。

### 7.4 自动评测的两个假阴性

优化后仍有两条记录未达到100%关键词覆盖，但人工判断答案正确：

- Q026回答“处理接口超时”，自动关键词要求连续文本“超时处理”，属于词序不同但语义一致；
- Q031只询问验收标记和保存期限，回答正确给出对应标记和210天，但自动规则还要求问题没有询问的柜号。

因此平均关键词覆盖率和完整覆盖数只适合作为快速提示，不能代替人工正确性判断。

### 7.5 来源评测器的限制

当前`source_pass`检查所有预期来源是否出现在“参考来源”中，但不会检查是否额外混入错误来源。

Q018同时列出正确Markdown和错误表格DOCX时，自动来源仍判为`true`。人工复核会进一步检查回答是否使用了不属于目标实体的内容，因此人工结论更严格。

## 9. 已知限制与后续计划

### 9.1 当前限制

1. 固定评测集只有5份文档和40道问题，不能等同于通用企业知识库准确率。
2. 云端模型输出仍存在随机性，即使重写温度为0，供应商实现和最终回答模型仍可能产生波动。
3. Prompt属于生成约束，不是程序级硬过滤；相似流程同时进入上下文时仍可能发生混用。
4. 自动关键词只能检查字面匹配，可能产生语义正确但自动失败的假阴性。
5. 自动来源判断只检查预期来源是否出现，不能发现额外错误来源。
6. Reranker超时后只回退粗排Top-3，正确证据排位较后时仍存在丢失风险。
7. 当前不支持扫描PDF、OCR、图片文字、复杂嵌套表格和合并单元格视觉布局还原。

### 9.2 后续可选增强

如果相似实体混用在更多真实资料中重复出现，可按以下顺序增强：

1. 入库时增加文档实体、项目或业务名称metadata；
2. 检索后按实体和来源文件分组；
3. 进入生成层前，由程序过滤不匹配实体的来源；
4. 增强来源评测器，检查是否出现预期外来源；
5. 增加检索层评测字段，分别记录粗排、精排和最终采用Chunk。

只有当真实日志持续证明正确证据频繁无法进入向量粗排Top-K时，再考虑：

- BM25：适合精确词、罕见编号、命令、产品型号等字面匹配；
- RRF：适合把向量排序和关键词排序等多个独立排名稳定合并；
- 混合检索：适合知识库同时存在语义表达差异和大量精确关键词的场景。

## 10. 面试复述摘要

我先为项目建立了5份固定测试文档和40道问题，覆盖五种文件格式、跨Chunk、多文件消歧、多轮追问、文末信息和知识库外拒答。部分题目重复运行，所以每轮有52条正式记录。评测时我没有只看最终答案，而是结合粗排Top-10、Reranker Top-3、最终上下文和问题重写日志定位失败：有的问题是正确Chunk没进粗排，有的是重写机械继承历史谓词，还有的是正确资料已经找到，但生成时遗漏关键信息或混入其他来源。基于这些证据，我只增加了单一文件类型metadata过滤，并收紧问题重写和最终回答Prompt，没有改Top-K、模型和数据库。人工严格通过率从46/52提升到51/52，稳定通过问题从35/40提升到39/40，但这只是固定测试集结果，不是生产环境通用准确率。没有直接上BM25、RRF或混合检索，是因为编号、代码和命令题已经表现良好，当前主要问题并非普遍漏召回。BM25更适合精确字面匹配，RRF适合融合多路排名，混合检索适合同时需要语义和关键词召回的知识库。当前剩余限制是相似业务片段进入同一上下文后，Prompt仍不能保证百分之百隔离，后续可增加实体metadata和生成前程序化过滤。

### 11.2 运行示例

确保后端已经由测试人员单独启动，并且测试知识库只包含5份固定文档，然后执行：

```powershell
.\.venv\Scripts\python.exe evaluation\run_rag_baseline.py --base-url http://127.0.0.1:8000 --username <测试用户名>
```

脚本会通过`getpass`安全读取密码，不在命令行回显密码，也不会把JWT写入结果CSV。

试运行指定题目：

```powershell
.\.venv\Scripts\python.exe evaluation\run_rag_baseline.py --base-url http://127.0.0.1:8000 --username <测试用户名> --questions Q001,Q024,Q038
```

全量运行时不传`--questions`，脚本按`repeat_count`生成52条正式记录。每次运行先生成`rag_baseline_results.csv`，确认无误后再由测试人员手动归档为对应阶段的基线文件。

### 11.3 指标口径

- HTTP成功率：`http_status`为200的记录数除以全部正式记录；
- 平均关键词覆盖率：所有非空`required_keyword_coverage`的算术平均；
- 关键词完整覆盖：`required_keyword_coverage`等于1的记录数；
- 来源命中：有预期来源的记录中，`source_pass`为`true`的数量；
- 自动拒答：拒答题中`refusal_pass`为`true`的数量；
- 延迟：正式问题从发送到SSE回答结束的`total_ms`；
- 严格通过：人工同时检查正确性、完整性、混淆和来源纯净度；
- 问题级稳定通过：同一道题的全部重复记录都严格通过。
